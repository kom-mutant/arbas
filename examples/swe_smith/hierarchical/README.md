# Иерархия поверх SWE-smith

Это исходный пример Agent Lightning с заменой одиночного агентского цикла
на создание исполнителей и последовательные назначения из MultiAgents.
Реализованы создание исполнителей, передача сообщений и выбор модели через
LinUCB из ORACLE. ARES пока не подключён.

```text
run.py       подготовка Smith → Orchestrator.run() → патч → оценка → награда
agents.py    Orchestrator, SubAgent, два инструмента и вызов OpenAI SDK
smith.py     перенесённые функции окружения и оценки Smith
types.py     настройки модели, описание агента, задание, результат, аргументы инструментов
config.py    настройки запуска и select_subagent_settings()
prompts.py   инструкции оркестратора и профили research / fix / verify
routing.py   выбор модели ORACLE, отложенная обратная связь и checkpoint
oracle/      нужные части исходного ORACLE: LinUCB, признаки, награда и контекст
```

## Один запуск

1. `run.main()` получает задачу и метаданные тем же способом, что Smith.
2. `checkout_bug_commit()` и `relocate_git()` готовят репозиторий.
3. Оркестратор вызывает `create_subagent(name)` и получает имя исполнителя.
4. `assign_task(agent, prompt, context)` сразу вызывает `SubAgent.execute()`.
   Исполнитель получает исходную задачу, назначение и явно переданный контекст.
5. Исполнитель вызывает Bash через `_forbidden_action()`, `_run()` и
   `render_observation()` Smith. Он возвращает отчёт, статус и расход токенов.
6. Оркестратору передаются только статус, отчёт и ошибка. После чтения отчёта
   он решает, что делать дальше. Bash у оркестратора нет.
7. При семантической обратной связи в конце эпизода судья оценивает каждое
   назначение по сохранённым данным. Веса субагентов при этом не обучаются.
8. Smith получает патч **до** восстановления скрытых тестов и оценивает решение.
   ORACLE обновляется по оценкам назначений; затем `agent_output` и итоговый
   `reward` всей SWE-задачи отправляются в Lightning для оркестратора.

Файлы общие, истории сообщений отдельные для каждого назначения. Повторное
назначение одному исполнителю тоже начинает новую историю. Оба агента завершают
диалог обычным непустым ответом без инструмента. `completed` означает полученный
отчёт; успешность решения определяет итоговая оценка Smith.

В `agents.py` нет наследования, очереди, реестра инструментов и менеджера контекста.
Сохранены два отдельных цикла по примеру MultiAgents. Клиент — OpenAI SDK,
который уже использует Smith. Pydantic описывает данные и аргументы инструментов.

## Что изменено в готовом коде

В `smith.py` без изменения реализации перенесены подготовка Git, восстановление
тестов, фильтры команд, форматирование наблюдения, получение метаданных, разбор
результатов pytest и функции штрафов из исходного примера.

Пять функций получили локальные исправления:

- `_agent_env()` исключает ключи обоих API из окружения Bash;
- `_run()` завершает также дочерние процессы после команды и таймаута;
- `post_event()` ограничивает повторы и прекращает их при ошибке авторизации;
- `capture_patch()` включает новые неигнорируемые файлы;
- `evaluate()` проверяет код выхода pytest, сравнивает полные пути тестов
  и загружает установленный pytest до исходников проекта.

Случайная задержка перед Git checkout выставлена в ноль.
В MultiAgents заменены поисковые инструменты, очередь заданий, профили и промпты.
Создание агента, отдельная история выполнения и возврат `TaskResult` сохранены.

## Запуск

Как и исходный Smith, программа запускается **внутри свежего подготовленного
контейнера SWE-smith** с репозиторием `/testbed`, веткой `instance_id` и установленными
зависимостями проекта. Она сама не создаёт контейнер и не клонирует репозиторий.
Ограничения команд Smith не заменяют изоляцию контейнера.

Из корня этой копии установите зависимости:

```bash
python -m pip install -r examples/swe_smith/hierarchical/requirements.txt
python -m examples.swe_smith.hierarchical.run
```

Основные переменные:

| Переменная | Назначение |
| --- | --- |
| `AGL_TASK_INPUT` | Исходная задача. |
| `AGL_EVAL_META` | JSON с instance_id, repo, FAIL_TO_PASS, PASS_TO_PASS; иначе запрашивается у Lightning. |
| `AGL_OPENAI_BASE_URL`, `AGL_KEY` | Обучающий Gateway оркестратора. |
| `ORCHESTRATOR_BASE_URL`, `ORCHESTRATOR_API_KEY` | Прямой API оркестратора вместо Gateway. |
| `OPENROUTER_API_KEY` | Отдельный ключ исполнителей. |
| `SUBAGENT_BASE_URL`, `SUBAGENT_API_KEY` | Альтернативный API исполнителей. |
| `ORCHESTRATOR_MODEL`, `SUBAGENT_MODEL` | Модели. |
| `ORCHESTRATOR_REASONING`, `SUBAGENT_REASONING` | Необязательный JSON параметров reasoning для совместимого сервера. |
| `SMITH_MAX_TURNS`, `SUBAGENT_MAX_STEPS` | Лимиты шагов. |
| `HIER_OUTPUT_DIR` | Каталог итогового JSON; по умолчанию /tmp/hierarchical-smith. |

Другие настройки и значения по умолчанию находятся в `config.py`.
Перед **каждым назначением** оркестратор вызывает `select_subagent_settings()`.
Это единственная точка выбора настроек: без роутера она возвращает фиксированные
настройки, с роутером обращается к `ModelRouter.select()`. Сам роутер один раз
создаётся в `run.py` и передаётся оркестратору. ORACLE заменяет только модель;
настройки reasoning, температура и лимит ответа сохраняются. Внутри одного
назначения модель неизменна. В конце `run.py` вызывает
`router.feedback(scores, swarm.assignments)`: список содержит отдельную оценку
для каждого назначения. Обновление выполняется один раз, до отправки reward в Lightning.

Итоговый JSON содержит патч, оценку, настройки без ключей, отчёты, истории
и токены каждого агента. В каждом результате сохраняется `judgment` с оценкой,
объяснением, исходным ответом судьи и ошибкой.
Для каждого эпизода нужен отдельный каталог результатов.
При отсутствии `AGL_EVENT_URL` отправка событий пропускается.

Существующие `run.sh`, `pull_images.py` и `job-template-openai.yaml` подключены
к новому пакету; схема запуска сервера, контроллера и тренера прежняя. Образы
с тегом `:arbas` получают Pydantic, OpenAI SDK и NumPy.
Готовому образу с прежним тегом `:oracle` можно добавить тег `:arbas` без пересборки.
Старые `:openai` и `:agl-openai` не переиспользуются: в них нет NumPy.
В кластере требуется Secret `swe-smith-openrouter` с ключом `api-key` и сетевой
доступ из контейнера к API исполнителей. Веса обучаются только по обращениям
оркестратора через Gateway; исполнители используют отдельный endpoint.

## Как включить ORACLE

В `hierarchical/oracle/` находятся только используемые части исходного `ORACLE/`:

```text
oracle/
├── __init__.py
├── bandit.py      LinUCB и его вспомогательная функция
├── base.py        базовый селектор, проверка награды и save/load
├── features.py    HashingFeatures
├── reward.py      Reward
└── types.py       RoutingContext
```

Реализации алгоритма и признаков сохранены. Изменены относительные импорты;
декоратор регистрации заменён полем `LinUCB.name = "linucb"` внутри класса.
Перенесены только части ORACLE, нужные для LinUCB. Формула награды сохранена;
оценку судьи проверяем при разборе ответа, а не повторно внутри формулы.
Сервер, DISC и реестр селекторов не переносились. Идея `LLMJudgeVerifier`
адаптирована в `evaluate_assignment()` в `run.py` под наш синхронный SDK, доказательства и JSON-оценки.
Устанавливать ORACLE отдельно не требуется: импорты относительные.

В подготовленном SWE-smith-контейнере задайте пул реальных API-идентификаторов
моделей, доступных на вашем `SUBAGENT_BASE_URL`. Значения ниже нужно заменить:

```bash
export ORACLE_MODELS='["YOUR_0_8B_MODEL_ID", "YOUR_2B_MODEL_ID", "YOUR_4B_MODEL_ID", "YOUR_9B_MODEL_ID"]'
export ORACLE_CHECKPOINT=/results/oracle/linucb.pkl
python -m examples.swe_smith.hierarchical.run
```

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `ORACLE_MODELS` | `[]` | JSON-список разных имён моделей одного API. Пустой список отключает роутер. |
| `ORACLE_CHECKPOINT` | `/tmp/hierarchical-oracle/linucb.pkl` | Полное состояние LinUCB между эпизодами. |
| `ORACLE_LEARN` | `true` | При `false` выполняется только выбор модели, без записи checkpoint. |
| `ORACLE_COST_WEIGHT` | `0.2` | Вес стоимости в функции награды ORACLE. |
| `ORACLE_COST_REF` | `10000` | Число выходных токенов, соответствующее нормированной стоимости 1. |
| `ORACLE_SEED` | `0` | Начальное случайное состояние нового селектора. |
| `ORACLE_FEEDBACK` | `semantic` | Отдельные оценки судьи; `episode` — общий raw_reward, прежний baseline. |

Профиль, текст подзадачи, переданный контекст и исходная SWE-задача превращаются
в 64 признака через готовый `HashingFeatures`. Это простые хешированные признаки
текста, а не обученная модель сложности. Текущая подзадача помещена первой,
поскольку экстрактор обрабатывает только первые 512 токенов своего разбиения.
Селектор выбирает модель непосредственно перед запуском исполнителя. При
повторном назначении тому же исполнителю выбор производится заново.

Обратная связь приходит **после завершения всей SWE-задачи**:

```text
score = оценка судьи для конкретного назначения
cost  = usage.completion_tokens конкретного назначения
reward = (1 - alpha) * score - alpha * min(cost / cost_ref, 1)
```

Формулу вычисляет оригинальный `Reward`. Успешный текстовый отчёт исполнителя
не считается проверкой правильности. В режиме `episode` вместо судьи используется
общий `raw_reward`, без штрафов Lightning за длину истории оркестратора.
Стоимость здесь — выходные токены,
сообщённые API, включая reasoning, если сервер учитывает его в этом поле.
Это не денежная стоимость: цена и размер выбранной модели отдельно не штрафуются.
Параметры `0.2` и `10000` — стартовые настройки эксперимента, их нужно подбирать.

### Семантический судья

Судья вызывается в конце эпизода, до восстановления скрытых тестов. Он видит
исходную проблему, конкретную подзадачу и контекст, инструкции исполнителя,
отчёт, наблюдения Bash,
а также накопленные патчи непосредственно до и после назначения. Эти снимки
сохраняются во время работы исполнителей: поздние правки не приписываются
ранним назначениям. Судье не передаются имя/модель исполнителя, стоимость,
общий итог SWE-проверки и внутренние рассуждения исполнителя.

Ответ — JSON `{"score": 0.8, "reason": "..."}`. Диапазон 0–1 проверяется Pydantic.
Ошибка API, невалидный JSON, отсутствующая оценка или обрыв генерации оставляют
`score=null`: соответствующий выбор модели пропускается при обучении. Это не
нулевая награда, и общая SWE-оценка вместо ошибки не подставляется. Остальные
корректные оценки того же эпизода используются обычным образом.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `JUDGE_BASE_URL` | API исполнителей | Прямой OpenAI-совместимый API судьи. |
| `JUDGE_API_KEY` | Ключ исполнителей | Отдельный ключ при необходимости. |
| `JUDGE_MODEL` | `ORCHESTRATOR_MODEL` | API-идентификатор модели-судьи. |
| `JUDGE_MAX_TOKENS` | `1024` | Лимит ответа судьи. |
| `JUDGE_REASONING` | `null` | JSON reasoning-настроек сервера. |

Передавайте реальный идентификатор модели, поддерживающей JSON-ответы. Температура
судьи равна нулю. Судья получает сохранённые наблюдения и патчи без дополнительной
обрезки. Он не получает инструментов и не запускает команды.

```bash
export ORACLE_FEEDBACK=semantic
export JUDGE_MODEL=YOUR_JUDGE_MODEL_ID
export ORACLE_CHECKPOINT=/results/oracle/semantic-experiment.pkl
```

Можно использовать модель оркестратора с другим промптом: задайте её прямой
`JUDGE_BASE_URL`, `JUDGE_MODEL` и при необходимости `JUDGE_API_KEY`. Через
Lightning rollout Gateway обращаться нельзя: он записывает все запросы, включая
валидационные, и отдельная история сама по себе не исключает судью из обучения.
Адрес судьи задаётся при запуске; код его не проверяет.

Для сравнения с общей наградой выставьте `ORACLE_FEEDBACK=episode`: судья и
снятие промежуточных патчей отключаются. Для разных способов оценки используйте
разные checkpoint, чтобы не смешивать статистику. При `ORACLE_COST_WEIGHT=0`
награда равна оценке качества без штрафа за токены.

Оценка судьи — экспериментальный сигнал, не доказательство правильности и не
оценка причинного вклада в общий успех. Её нужно проверить на ручной выборке.
Штраф за токены считается по расходу исполнителя.
В обычной валидации оценки сохраняются, но ORACLE не обновляется.

LinUCB сохраняется готовым методом `save()`, включая матрицы и состояние RNG.
При нескольких процессах выбор и обновление выполняются под файловой блокировкой
с повторной загрузкой актуального состояния; запись заменяет файл атомарно.
Блокировка не держится во время работы модели или Bash. Для каждого нового
эксперимента используйте отдельный checkpoint; при изменении пула моделей тоже
нужен новый файл. Интеграция рассчитана на Linux/macOS. После переноса ORACLE
внутрь проекта старые pickle-checkpoint внешнего пакета нужно заменить новыми.
Сохраняйте одинаковый способ запуска для эпизодов, использующих один checkpoint:
pickle записывает полное имя Python-модуля класса селектора.

Для валидации задайте `ORACLE_LEARN=false`. Адрес Lightning с `/mode/val/`
также автоматически отключает обновления и запись checkpoint. Выбор использует
загруженный селектор с прежним правилом LinUCB; отдельная жадная политика оценки
не добавлялась. Для первого сравнения держите оркестратора и reasoning фиксированными.

В итоговом JSON появляется `oracle`: выбранные модели, признаки и исходный текст
выбора, стоимость, оценка, награда и факт обучения для каждого назначения.
Идентификаторы назначений уникальны между эпизодами.

### Существующий запуск Lightning

При запуске `run.sh controller` экспортируйте `ORACLE_MODELS` на машине контроллера:
скрипт передаст список, `ORACLE_FEEDBACK`, `JUDGE_BASE_URL` и `JUDGE_MODEL` через
существующий ConfigMap. Для отдельного ключа судьи задайте `JUDGE_API_KEY` в
шаблоне через Kubernetes Secret, не через ConfigMap. Подпапка `oracle/` передаётся
вторым ConfigMap, поскольку `--from-file` не обходит вложенные папки. Сначала подготовьте новые
образы с помощью `pull_images.py`. Шаблон задания использует checkpoint
`/agl-logs/oracle/linucb.pkl`, который переживает удаление контейнера на том же узле.

В шаблоне `/agl-logs` — `hostPath`, то есть диск **одного узла**, а не общее хранилище
кластера. Для единого обучения на нескольких узлах замените этот том общим
хранилищем с поддержкой файловых блокировок. Для прямого запуска контейнера
аналогично смонтируйте каталог checkpoint снаружи; `/tmp` внутри удалённого
контейнера не обеспечивает накопления обучения между контейнерами.

### Первый шаг GRPO

На GPU-сервере из корня репозитория, с `uv` в `PATH`:

```bash
bash examples/swe_smith/setup_training.sh
source .venv/bin/activate
```

Это один набор зависимостей для короткого и обычного обучения на Linux x86_64
с Python 3.12 и CUDA 12.9. Установщик собирает пакет veRL 0.8.0 с изменениями
из [veRL #6551](https://github.com/verl-project/verl/pull/6551) для NumPy 2,
сохраняя интерфейс тренера Agent Lightning. FlashAttention и causal-conv1d
скачиваются готовыми сборками под PyTorch 2.11.0 и CUDA 12.9.

Параметры эксперимента находятся в [`training.yaml`](../training.yaml).
`actor_rollout_ref.model.path` задаёт модель оркестратора. Там же
`lora_rank: 0` означает обучение всех параметров, а, например, `lora_rank: 16`
включает LoRA. В этом же файле задаются learning rate, число GPU и попыток на
задачу, лимиты контекста, датасеты, пул моделей ORACLE и модель судьи. Блок
`smoke` переопределяет настройки короткого прогона. Для отдельного конфига
задайте `AGL_TRAIN_CONFIG` на обеих машинах. Ключи и адреса подключения
задаются отдельно через переменные окружения и Kubernetes Secret.

В `smoke_train.jsonl` и `smoke_val.jsonl` лежат две реальные
задачи `oauthlib` из [SWE-smith-py](https://huggingface.co/datasets/SWE-bench/SWE-smith-py)
на одном образе. Сохранены все FAIL_TO_PASS и только те PASS_TO_PASS, что лежат
в тех же файлах, как при `SMITH_F2P_ONLY=1`. Эталонные патчи не включены.

1. Там, где готовятся образы для Kubernetes, соберите `:arbas` и убедитесь, что
   кластер видит этот тег. В выделенном namespace нужен Secret `swe-smith-openrouter`
   с ключом `api-key`.

   ```bash
   python examples/swe_smith/pull_images.py \
     --dataset examples/swe_smith/smoke_train.jsonl \
     --dataset examples/swe_smith/smoke_val.jsonl
   ```

2. На GPU-сервере запустите `bash examples/swe_smith/run.sh server`. Для сервера,
   контроллера и тренера используйте один `AGL_KEY`. На машине с
   доступом к Kubernetes задайте `AGL_NAMESPACE` и `AGL_SERVER_PUBLIC_HOST` —
   адрес GPU-сервера, доступный контроллеру и контейнерам. Затем запустите контроллер:

   ```bash
   bash examples/swe_smith/run.sh controller --smoke
   ```

   Один вариант модели исполнителя здесь достаточен: проверяем получение оценки
   и время судьи. Состояние ORACLE для этого теста не обновляется.

3. В другом терминале GPU-сервера запустите `bash examples/swe_smith/run.sh trainer --smoke`
   на одной выделенной GPU. Профиль даёт четыре попытки на одну задачу и один шаг
   GRPO; валидация, возобновление и сохранение весов отключены.

Для обычного обучения запустите контроллер и тренер без `--smoke`. Укажите свои
подготовленные JSONL в `data.train_files` и `data.val_files`.

На каждой машине `run.sh` сохраняет логи своих процессов в `outputs/swe-smith`.
Задайте `AGL_RUN_DIR`, чтобы разделить запуски. На GPU-сервере там же сохраняются
метрики TensorBoard. Логи отдельных задач Kubernetes лежат на узле кластера в
`/agl-logs/new`. Чтобы открыть TensorBoard на машине с логами тренера:

```bash
tensorboard --logdir outputs/swe-smith/tensorboard --host 127.0.0.1
```

В логе тренера проверьте `training/n_rollouts_w_reward` (ожидаем 4),
`training/n_sample_trained` (больше нуля), `timing_s/update_actor` и
`timing_s/update_weights`. Последние две метрики показывают, что вызовы обновления
актора и передачи весов в vLLM завершились. Для проверки сигнала GRPO
`training/n_zero_adv_groups` должно быть меньше `training/n_groups`. При одинаковых
наградах прогон проверяет выполнение шага, но не подтверждает изменение параметров
от сигнала GRPO. В логах контейнеров `Judge stage` показывает число оценённых
назначений и время этапа, а `rollout_wall_s` — время всей попытки.

Проверка без внешних API и GPU:

```bash
python -m pytest tests/examples/test_hierarchical_agent.py \
  tests/examples/test_swe_smith_agent.py tests/examples/test_swe_smith_images.py -q
```
